Juno is a monorepo of NestJS services. Docker Compose starts all of them (plus Postgres) together, and pnpm scripts wrap the Docker commands for you.

## Prerequisites

- [Docker Desktop](https://www.docker.com/products/docker-desktop/) v4.24 or newer
- [pnpm](https://pnpm.io/installation)
- [protoc](https://github.com/protocolbuffers/protobuf/releases) v28.2
- WSL2 if you're on Windows

<Warning>
  Homebrew tends to ship an older `protoc` that doesn't work with Juno. Install
  the binary from the protobuf releases page instead.
</Warning>

<Note>
  On Windows, do everything inside WSL, including cloning the repo. The repo has a `.gitattributes` with `*.sh text eol=lf` so shell scripts keep Unix line endings, but if you cloned before that landed, re-clone or run `git add --renormalize .`. CRLF line endings in `docker/*.sh` are what cause the `<>.sh: not found` Docker build failures.
</Note>

## Start the stack

```bash
git clone https://github.com/GTBitsOfGood/juno.git
cd juno
pnpm install
pnpm start:dev:live-all
```

`start:dev:live-all` builds the images, starts every service, and live-reloads when you edit files under `packages/`. Add `--build` to force a full rebuild when Docker's cache is being weird:

```bash
pnpm start:dev:live-all --build
```

The API gateway is exposed on **`http://localhost:8888`**. Swagger UI for the live gateway is at `http://localhost:8888/docs`.

## Seeded data

To wipe your database and reseed it, run:

```bash
pnpm start:dev:live-all-reseed
```

Reseeding creates, among other things:

| What                | Value                      |
| ------------------- | -------------------------- |
| Superadmin email    | `test-superadmin@test.com` |
| Superadmin password | `test-password`            |
| Project             | `test-seed-project`        |

Use that superadmin to approve account requests and create projects in a local copy of the dashboard. These are test credentials for a throwaway local database only. Production has its own superadmin.

## Environment variables

Services read their config from `docker-compose-dev.yml`, plus two optional, git-ignored env files in the repo root:

- `.env.dev.local` for anything you want to override locally
- `.env.gh-actions.local` for the file-service tests' storage credentials (`accessKeyId`, `secretAccessKey`, `baseURL`). CI generates this from repo secrets.

| Variable           | Used by       | Notes                                                                                     |
| ------------------ | ------------- | ----------------------------------------------------------------------------------------- |
| `JWT_SECRET`       | auth-service  | Signs user and API key JWTs. Falls back to a dev default, so always set it in production. |
| `SENDGRID_API_KEY` | email-service | A fake `test-key` is used by default in dev.                                              |
| `*_SERVICE_ADDR`   | every service | Where to find the other services. Compose sets these for you.                             |
| `SENTRY_DSN`       | every service | Optional error reporting.                                                                 |

## Testing

E2E tests run inside Docker through Jest:

```bash
pnpm test:e2e:api-gateway
pnpm test:e2e:auth-service
pnpm test:e2e:db-service
```

Each service also has a `-live` variant (for example `pnpm test:e2e:api-gateway-live`) that re-runs tests as files change.

## Changing protobuf definitions

After editing a `.proto` file, rebuild and sync the generated types into every service:

```bash
pnpm gen-proto
pnpm sync-protos
```

## Changing database schemas

Juno uses Prisma in `db-service`. With the stack running:

```bash
DATABASE_URL=postgresql://user:password@localhost:<port> \
  pnpm prisma migrate dev --schema=<path to schema.prisma>
```

Then check that a new folder showed up under `migrations`. In production, `db-service` runs `prisma migrate deploy` on startup, so committed migrations apply on their own when a new image rolls out.

## Testing against a local SDK

If you changed a route and want to try the SDK against it before it's released, link your local `juno-sdk` build into your app and point `baseURL` at your local gateway.

<Steps>
  <Step title="Refresh the SDK's generated client">
    With Juno running, run the `scripts/doc-extract-macos.sh` (or `doc-extract-window.sh`) script. It downloads the gateway's OpenAPI spec and runs the OpenAPI generator into `juno-client-sdk/`. Copy `api.ts` plus the `api` and `model` folders into the `juno-sdk` repo's `src/internal`.
  </Step>

{' '}

<Step title="Build and link the SDK">
  ```bash # in the juno-sdk repo bun run build npm link ```
</Step>

  <Step title="Use it from your app">
    ```bash
    # in your app
    npm link juno-sdk
    ```

    ```ts
    import juno from 'juno-sdk';

    juno.init({
      apiKey: process.env.JUNO_API_KEY!,
      baseURL: 'http://localhost:8888',
    });
    ```

  </Step>
</Steps>

If you don't want to link, `"juno-sdk": "file:../juno-sdk"` in your `package.json` works too.

## Keeping the API reference current

The API reference is rendered from `docs/openapi.json`, a snapshot of the gateway's `/docs-json`. When routes change, refresh it from a running gateway:

```bash
curl http://localhost:8888/docs-json | jq . > docs/openapi.json
```

The `servers` list in the snapshot comes from `.addServer(...)` in `packages/api-gateway/src/main.ts`.

## Troubleshooting

- `db-service is unhealthy`: shell scripts probably lost their executable bit. Run `chmod +x packages/db-service/entrypoint.sh`.
- `<>.sh: Permission denied`: same fix, `chmod +x` the script.
- `additional property <> is not allowed`: update Docker Desktop to v4.24 or newer.
- `Failed to connect. Is Docker running?` in VS Code: make sure Docker Desktop is running, and re-enable WSL integration under **Settings > Resources > WSL integration**.
- Forgot to install `protoc`: install it and re-run `pnpm gen-proto`.
